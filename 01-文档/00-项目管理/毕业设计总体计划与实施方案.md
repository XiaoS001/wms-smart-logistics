## 第一部分　总目标与总体思路

### 1.1 最终交付物（四件套）

| 序号 | 交付物 | 验收口径 |
|---|---|---|
| D1 | 可运行的仓储管理系统 | 9 个功能模块，前后端可启动，含货位优化与拣货路径规划 |
| D2 | 算法对比实验数据与图表 | 货位分配 3 策略、拣货路径 4 策略的横向对比，可复现 |
| D3 | 毕业论文 | 理工科 ≥8000 字（本项目按 ≥12000 字），重复率 ≤20%，参考文献 ≥15 篇（外文 ≥2 篇） |
| D4 | 过程材料 | 开题报告、中期检查表、答辩 PPT、部署说明 |

### 1.2 核心思路（一句话）

> 用**常规业务模块**撑起工程体量，用**两类优化算法 + 可量化对比实验**撑起论文内核；算法先独立跑通并产出数据，再嵌入系统界面。

### 1.3 必须守住的三条线

1. **算法线**：K1–K5 五个关键问题必须有真实实现、真实数据、真实对比，绝不写虚。
2. **数据线**：所有实验数据由脚本生成、可复现，禁止手工编造或修改数据迎合指标。
3. **格式线**：所有文档按学校规范排版，参考文献用知网导出格式，避免后期返工。

## 第五部分　分步执行方式（防错机制）

### 5.1 每一步的标准流程（六步法）

```
① 明确本步目标与验收标准
② 只做一件事，改动范围写清楚
③ 执行（写代码 / 写文档）
④ 立即验证（能编译的编译、能跑的跑、文档跑结构检查）
⑤ 记录到进度看板（做了什么、验证结果、遗留问题）
⑥ 验证通过才进入下一步
```

**核心纪律：一次只推进一件事；每步必须有一次机器验证。**

### 5.2 本项目的验证手段（对应不同产出）

| 产出类型 | 验证方式 |
|---|---|
| Java 代码 | `mvn -q compile` 编译通过；接口用 curl/浏览器实测 |
| 前端代码 | `npm run build` 构建通过；页面手工点一遍 |
| SQL 脚本 | 在 MySQL 中实际执行，`SHOW TABLES` 数量核对 ≥15 |
| 算法代码 | 单元测试 + 小规模算例与穷举最优解对拍 |
| Word/Excel 文档 | 用 `check_office.py` 做结构与内容检查 |
| Markdown 文档 | 结构自检（章节完整性、无占位符残留） |

### 5.3 文档与代码的版本约定

- 文档命名：`主题-版本-日期`，如 `开题报告-v1-20261020.docx`
- 实验命名：`实验名-参数-日期`，如 `路径规划对比-S型vs蚁群-20270115.xlsx`
- 重要节点（里程碑）前，对 `01-文档` 与 `03-源码` 各做一次整体备份
- 建议在 M1 后把 `03-源码` 纳入 Git 管理（本机已有 Git）

## 第六部分　风险识别与应对（出现问题怎么办）

> 每个风险给出：**现象 → 预案 → 触发条件**。按严重程度排序，前三条是致命风险。

### R1　算法指标不达标 ★致命

- **现象**：路径长度降幅不足 10%、或行走距离降幅不足 15%、或 100 拣货点计算超过 1 秒。
- **预案（按顺序）**：
  1. **先查实现**：距离矩阵、约束、目标函数是否写错（最常见是距离计算出错而非算法无效）
  2. **调参**：GA 增大种群与迭代数、调交叉/变异概率；ACO 调信息素挥发因子 ρ 与 α/β
  3. **加策略**：货位分配引入 ABC 分类分区；路径规划引入 2-opt 邻域优化
  4. **如实记录**：若仍不达标，在论文中**作为参数敏感性分析结论写明**，分析原因
- **禁止**：修改实验数据、删除不利结果。任务书与规范均要求如实记录。
- **触发条件**：M1 时第一版数据不达标 → 立即执行预案，不拖延。

### R2　环境与依赖不可用 ★高

- **现象**：JDK/Maven 下载失败；Maven 依赖拉取超时；MySQL 初始化失败或端口被占。
- **预案**：
  1. Maven 换阿里云镜像（`settings.xml` 加 `<mirror>`）
  2. 依赖仍失败 → 用 `-o` 离线模式配合已下载的本地仓库，或改用 Spring Boot 更低小版本
  3. MySQL 3306 端口被占 → 改 3307；`--initialize` 失败 → 清空 datadir 重来
  4. 若长期无法装 Java → **降级方案**：后端改用 Node.js（Express/NestJS）实现，前端不变，**需先与指导老师确认**
- **触发条件**：连续两次安装尝试失败。

### R3　时间不够（开发拖期挤占论文时间）★高

- **现象**：P3/P4 编码阶段超出预定周数。
- **预案**：
  1. **保内核**：优先保算法（K1–K5）与论文；9 个模块中砍掉非核心的锦上添花功能（如复杂报表美化）
  2. **降范围**：先做「最小可用闭环」——登录、仓库/库位、商品、入库、出库、库存、两个算法模块，其余按剩余时间补
  3. **并行推进**：算法完成后即开始写论文第 3、4 章，不等到系统做完
- **触发条件**：任何阶段超期 1 周以上。

### R4　功能范围蔓延 ★中

- **现象**：不断加新想法（多仓库、RFID、数字孪生、移动端…），主线被拖散。
- **预案**：回到任务书的 **9 个模块清单**，新增想法一律记入「待办/加分项」清单，**版本 1.0 不做**。

### R5　系统与算法融合困难 ★中

- **现象**：算法嵌进业务流程后接口混乱、响应变慢。
- **预案**：一开始就采用**算法独立服务层**设计（算法模块不依赖 Web 框架，可被单元测试直接调用），系统侧只通过 Service 接口调用。这也是论文的一个设计亮点。

### R6　实验环境不可复现 ★中

- **现象**：实验数据无法解释来源，评委追问细节答不上。
- **预案**：所有实验数据由脚本生成，脚本带固定随机种子；保存「实验配置 + 原始输出 + 结果表 + 图表」四件套到 `04-测试与实验\`。

### R7　查重率偏高 ★中

- **现象**：系统类章节描述与其他论文雷同。
- **预案**：第 3、4、6 章以自建模型、自写代码、自制数据为主；引用处规范标注；避免大段复制百科式技术介绍。

### R8　格式返工 ★低但耗时

- **预案**：从第一份文档起就按规范排版（页边距、字体字号、三线表、图表编号），并用 `论文撰写规范-要点摘录.md` 第十二章自检清单逐项核对，避免最后集中返工。

### R9　文档丢失 / 覆盖 ★低但后果重

- **预案**：里程碑节点整体备份；`Readme.md` 之外的成品文档只增不改（改则新建版本）；Git 管理代码。
